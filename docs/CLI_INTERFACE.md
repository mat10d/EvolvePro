# Target CLI interface

This document records the target user-facing CLI after the migration. It is a UX contract, not the current implementation. Existing `evolvepro run`, `evolvepro process ...`, and `evolvepro dms grid-search` commands remain compatibility scaffolding until the target interface is implemented and regression-tested.

## Design goal

The CLI should expose business workflows, not low-level file processing operations. A normal user should not need to manually call commands for WT FASTA generation, single-mutant library generation, dataset preprocessing, or round-specific training internals.

The primary workflow is:

```bash
evolvepro init my-protein
evolvepro evolve
# fill activity values in the generated candidates CSV
evolvepro evolve
evolvepro validate
evolvepro plot
```

One workspace manages one protein. Multiple proteins require multiple workspaces.

## Target command surface

| Command | Purpose | Interactive? | Notes |
|---|---|---|---|
| `evolvepro init [DIR]` | Create and configure a workspace for one protein. | Yes by default | Initializes workspace state and collects protein/workflow settings. |
| `evolvepro init [DIR] --set-default` | Create a workspace using default settings. | No | Default values are intentionally not finalized yet. |
| `evolvepro init [DIR] --reconfigure` | Reconfigure an existing workspace. | Yes unless `--yes` | Replaces the public `configure` command. Must warn before overriding existing config. |
| `evolvepro evolve` | Advance the workspace to the next useful state. | No | Generates initial candidates, ingests measured activity, trains, predicts, writes artifacts, and updates state. |
| `evolvepro validate` | Verify workspace, lock, manifest, and artifact integrity. | No | Also runs implicitly inside `evolve`. |
| `evolvepro plot` | Plot final or round-specific results. | No by default | `--interactive` may emit Plotly/HTML output. |
| `evolvepro dms ...` | Run DMS benchmark/simulation workflows. | TBD | DMS is separate from active-learning protein workspaces. |

## Public `configure` command decision

Do not expose `evolvepro configure` as a primary command.

`configure` is an internal phase of `init`:

- New workspace: `evolvepro init` performs interactive configuration.
- Existing workspace: `evolvepro init --reconfigure` performs interactive reconfiguration.
- Automation: `evolvepro init --set-default --yes` creates a workspace without prompts.

If an existing configuration would be overwritten, the CLI must prompt:

```text
Existing EvolvePro workspace configuration found.
Override it? [Y/n]
```

`--yes` is required for non-interactive overwrite.

## `evolve` state machine

`evolvepro evolve` is intentionally high-level. It should hide low-level sequencing, preprocessing, model training, prediction, checkpointing, and validation details behind a workspace state machine.

| Workspace state | `evolve` behavior |
|---|---|
| No workspace | Error with instruction to run `evolvepro init`. |
| Workspace exists but no valid config | Error or run the same setup flow as `init --reconfigure`. |
| Configured, no rounds | Generate initial candidate list from the configured protein sequence and mutation policy. |
| Latest round has candidates with blank activity values | Stop with clear message telling the user to fill the activity column. |
| Latest round has some measured activity values | Ingest measured rows, treat blank rows as unmeasured, train/update model, predict next candidates. |
| Previous lock/manifest/artifact hash mismatch | Stop. User must resolve integrity mismatch before continuing. |

The command should always run validation recursively over previous rounds before advancing.

## Candidate handoff CSV

The user-facing handoff file is a mutable CSV generated by `evolve`:

```csv
variant,activity
A12V,
G18D,
L22F,
```

User workflow:

1. Run `evolvepro evolve`.
2. Open the generated `candidates.csv`.
3. Fill only the `activity` values that were successfully measured.
4. Leave failed or unmeasured candidates blank.
5. Run `evolvepro evolve` again.

Partial experiments are normal. For example, if 15 candidates were proposed but only 12 were measured, the 12 filled rows become measured observations and the 3 blank rows are recorded as unmeasured.

## CSV-only policy for user handoff

Primary user input/output handoff files are CSV only.

Supported table shape:

```text
variant,activity
```

Rules:

- Exactly two columns: `variant` and `activity`.
- UTF-8 CSV with comma delimiter.
- Duplicate variants are invalid.
- Blank `activity` cells are allowed and mean unmeasured.
- Non-blank `activity` cells must parse as numeric values.
- Row order should be preserved for the user-facing file.
- Canonical table hashes define semantic identity for validation.

XLSX is not part of the primary handoff workflow because spreadsheet metadata, formatting, blank cells, and layout changes make byte-level provenance fragile. If legacy XLSX import is retained, it must be normalized immediately to canonical CSV and the rest of the workflow must use the CSV artifact.

## Mutable handoff vs immutable provenance

Generated candidate CSV files are intentionally user-editable, so they cannot be the sole immutable output artifact.

Every generated or ingested file must be snapshotted into content-addressed storage before it participates in validation:

```text
workspace/
  rounds/
    round_000/
      candidates.csv          # mutable handoff file
      manifest.json           # read-only ledger
      round.lock              # read-only round snapshot

  .evolvepro/
    cas/
      sha256/
        ab/cd/<hash>          # immutable snapshots
```

Validation uses the CAS snapshots and recorded hashes, not trust in the mutable handoff path.

## Hashing and integrity policy

Hash all inputs and outputs at every step. Final-result-only hashing is insufficient.

Each logical step records:

```text
input artifact hashes + parameters + code/environment metadata -> output artifact hashes
```

Required hash coverage:

| Artifact class | Required hashes |
|---|---|
| Raw user CSV | byte SHA256 and canonical table semantic hash |
| Generated candidate CSV | byte SHA256 and canonical table semantic hash |
| Normalized activity table | canonical table semantic hash |
| Embeddings | byte SHA256 and semantic hash where applicable |
| Model parameters | canonical JSON semantic hash |
| Model checkpoint | byte SHA256 |
| Predictions | canonical table semantic hash |
| Lock files | byte SHA256 over deterministic JSON |
| Manifest files | byte SHA256 over deterministic JSON |

## Lock file policy

Use `.lock` filenames, not `.lock.json`, for user-facing lock files. The internal encoding may remain deterministic JSON.

Target names:

```text
workspace/
  evolvepro.lock              # mutable global workspace index
  rounds/
    round_000/
      round.lock              # immutable per-round resolved snapshot
      manifest.json           # immutable per-round artifact ledger
```

Role split:

| File | Mutability | Role |
|---|---|---|
| `evolvepro.lock` | Mutable | Workspace index, latest round pointer, list of round manifest hashes. |
| `round.lock` | Immutable after write | Resolved inputs/config/model parameters for one round transition. |
| `manifest.json` | Immutable after write | Full input/output hash ledger and lineage for one round transition. |

Do not store per-round observations or experimental outcomes in the global config. The global config contains stable policy only. Round observations are artifacts/events recorded by round manifests.

## Read-only artifact policy

Read-only permissions are useful as a guardrail but are not the integrity mechanism.

Recommended permissions:

| File | Permission intent |
|---|---|
| CAS snapshots | read-only after atomic write |
| `round.lock` | read-only after atomic write |
| `manifest.json` | read-only after atomic write |
| `candidates.csv` | writable handoff file |
| `evolvepro.lock` | writable by EvolvePro during state updates |
| `evolvepro.toml` | writable through `init --reconfigure` or manual edits |

Integrity is enforced by hash validation. POSIX read-only bits only reduce accidental edits.

## Existing implementation mapping

| Current implemented command | Target status |
|---|---|
| `evolvepro init` | Keep and expand into full workspace setup/configuration. |
| `evolvepro run --config` | Compatibility/non-interactive scaffold. Its behavior should be absorbed by `evolve`. |
| `evolvepro validate [ROUND_DIR]` | Keep, but default to workspace-wide validation. |
| `evolvepro process generate-wt` | Compatibility/low-level utility. Not primary UX. |
| `evolvepro process generate-single-aa-mutants` | Compatibility/low-level utility. Not primary UX. |
| `evolvepro process dataset` | Compatibility/low-level utility. Dataset ingest should be implicit in `evolve`. |
| `evolvepro dms grid-search` | Compatibility scaffold for future `evolvepro dms ...`. |

## Implementation constraints

- Keep current compatibility commands until target commands have regression tests.
- Do not delete scripts until replacement commands and docs are complete.
- Keep torch/PLM dependencies optional for core CSV workflows.
- Make `evolve` deterministic and resumable.
- Treat failed or partial experimental measurements as normal state, not an edge case.
- Prefer additive migration: implement target commands first, then deprecate compatibility commands.
